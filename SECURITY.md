# Границы безопасности

## Компоненты и права

Gateway выполняет только исходящие HTTPS-запросы к официальному Telegram Bot API с long polling. Нет публичного HTTP, webhook, TCP App Server или проброса порта. Каждое сообщение и callback проверяет числовой from.id, private chat и chat.id. Username не участвует в авторизации. Controller повторяет проверку.

Gateway запускается **через bubblewrap**, а не просто под тем же Linux-пользователем. Новый mount/PID/IPC namespace содержит `/usr`, минимальные SSL/DNS файлы, Python/venv и код приложения, gateway.toml, модель/whisper-cli, read-only outbox, read-only каталог gateway Unix socket и собственный writable state. Домашний каталог, репозитории, Controller config, Codex auth, SSH/AWS и host `/proc` не доступны. Все capabilities сняты, среда очищена. Обход при отсутствии bubblewrap не предусмотрен.

Проверка реального namespace пытается прочесть fixture SSH, AWS, Codex auth, `.env`, Controller config и записать outbox; доступ запрещён. Эти проверки подтверждают выбранные границы, а не абсолютную изоляцию от уязвимостей ядра, Python, media libraries и файловых гонок.

Внешний launcher Gateway до запуска bubblewrap читает только необходимый локальный конфиг, но имеет обычные права пользователя. **Controller не изолирован от всех пользовательских файлов**, как и Codex. Он получает зарегистрированные пути и управляет сервером; его компрометация требует другой модели изоляции/отдельного Unix-пользователя. Сервисы `systemd --user` не дают отдельный UID. Ручной запуск внутреннего `gateway-worker` вне штатного launcher не изолирован и не является поддержанным deployment.

IPC использует SO_PEERCRED того же UID, приватные каталоги 0700 и socket 0600, ограниченный JSON frame 128 KiB и allowlist операций. Gateway не видит административный local.sock и App Server socket. Авторизованный процесс вашего пользователя вне sandbox может обращаться к административному IPC — он считается доверенным. IPC не принимает shell string, произвольный download path или установку пакетов.

## Codex и действия агента

Мост не исполняет Telegram-текст как shell: native queue получает типизированный input text. Approval responses используют структурированный RPC, связывают project/thread/session/turn/request ID и epoch соединения. Только accept once/decline; permission response копирует запрошенные права с scope turn. Просроченные/replayed/разрешённые локально requests не применяются снова. При ошибке доставки состояние блокируется и решение не повторяется.

Sandbox — workspace-write, approval policy — on-request, reviewer — user. API key environment variables удаляются из окружения App Server. Не используются yolo или отключение sandbox. При обновлении Codex version guard блокирует несовместимый протокол. Штатный local TUI может менять permissions и другие настройки: это действие доверенного локального пользователя, которое мост запретить не может.

Разрешённый текст может побудить самого Codex выполнить команды или прочесть файлы в рамках его прав. **On-request не требует разрешения для каждой команды**, а workspace-write не ограничивает всё чтение домашнего каталога. Секреты в допустимой сводке или изображении могут утечь; регулярные выражения не гарантируют распознавание всех секретов. Для строгой конфиденциальности нужны отдельный рабочий пользователь/контейнер Codex и отдельная политика доступа.

One Project — One Active Session обеспечивается зарегистрированными непересекающимися каталогами, единственным Controller lock, одним App Server и одной привязкой thread. При /new старый runtime закрывается через archive/unarchive; история сохраняется без resume старого writer. Bridge не создаёт независимые сессии на сообщения. Проверка `/proc` отвергает самостоятельный Codex в зарегистрированном cwd. Она **не доказывает отсутствие чужого app-server**, процесса другого UID или нештатного writer. Перед migrate пользователь действительно должен завершить старые writers. Не запускайте параллельный standalone resume.

`attach --current --force` доступен только через локальный административный IPC. До закрытия прежней сессии проверяются целевая история, UUID, canonical cwd, отсутствие subagent/ephemeral и привязки к другому проекту. Force адресует только прежний thread и его частный tmux-терминал; прерывание ждёт фактического завершения turn. Неизвестная доставка без turn ID не отбрасывается даже с force. Ошибка/тайм-аут после начала передачи оставляют очередь заблокированной; старые callbacks не переносятся в новую сессию. `--old-process-stopped` — подтверждение локального оператора, а не проверка чужого App Server. Отсоединение его TUI само по себе не гарантирует закрытия runtime. Force прерывает незавершённую работу, снимает нативные ожидающие сообщения прежнего чата и отсоединяет клиентов старого терминала; историю не удаляет и никаких approvals не принимает.

## Изображения и workflow gate

Publisher открывает проект-relative файл через directory FDs с O_NOFOLLOW для каждого компонента. Только regular file, link count 1, допустимый размер, стабильные fstat до/после чтения; real format проверяет Pillow. Hidden path components, symlink/hardlink, traversal, FIFO/device, animation и чрезмерные размеры отклоняются. Изображение перекодируется, metadata удаляется, export создаётся эксклюзивно с 0600. Gateway читает только экспорт по FD, проверяет имя/тип/линки/стабильность и не сканирует пользовательские каталоги. Замена исходника после открытия не меняет читаемый FD.

Проверки inode/link count защищают от обычного hardlink обхода. Они не защищают от намеренно действующего владельца каталога, всех типов mount/bind tricks или параллельного изменения байтов с восстановлением timestamps. Владелец проекта и локальные административные helper calls входят в доверенную область.

Публикация связывает export с текущим живым turn и opaque одноразовым token. После подтверждённой доставки export удаляется. При сбое между отправкой и ack возможна повторная доставка: Telegram API не предоставляет атомарной транзакции с нашей SQLite. Неотправленные exports после аварии сохраняются для доставки; проверяйте и удаляйте ненужные файлы вручную при остановленном мосте.

Dynamic tool оставляется без ответа до оценки; это реальный барьер для данного tool call и очереди. Helper блокирует вызывающий shell tool и возвращает nonzero для правок/отказа/потери связи. **Это не остановка всех параллельных процессов проекта** и не гарантия против намеренного обхода агентом через фоновые jobs. Зависимые этапы должны быть последовательными. Основной путь — dynamic tool, не длительный shell wait.

## Голос, секреты и сеть

Медиа проходит FFprobe-проверку OGG/Opus/длительности, FFmpeg и whisper.cpp в дополнительном namespace **без сети**. На обработку ограничены время, адресное пространство, CPU time и количество workers. Временные записи удаляются даже при ошибке/timeout. Содержимое голоса не пишется в journald. Голосовые команды не дают прав администрирования; транскрипт обязательно подтверждается.

Token хранится только в gateway.toml 0600 внутри приватного каталога 0700, не в SQLite, исходниках или command line. Опубликованный токен следует перевыпустить. Ошибки Telegram не выводят URL, который содержит token; debug access logs aiohttp не включены. Controller фильтрует известные секретные шаблоны и не передаёт raw tool outputs/JSONL/исходники/env. Пересылка финального ответа и встроенных imageGeneration-изображений выключена по умолчанию (`mirror_results=false`); setup предлагает включить её локально. Включённая пересылка фильтрует известные секретные шаблоны и ограничивает финальный текст 16 000 символами. Автоматический image export использует только bounded base64 result структурированного события своей сессии/turn, строгий decoder и ту же нормализацию Pillow; savedPath игнорируется, доступ к новым файловым каталогам не добавляется. Метаданные изображений удаляются, но секреты внутри пикселей автоматически не распознаются. Эта доставка не заменяет workflow gate.

SQLite временно сохраняет ожидающие задачи, вопросы, edits и транскрипты. После завершения/потребления текст очищается; acknowledgements удаляют notice body. Это не криптографическое стирание страниц, WAL и резервных копий. User ID находится только в локальных конфигах. Backup метаданных может содержать pending prompts; защищайте файл 0600 и его каталог 0700.

Telegram-боты **не используют E2E шифрование**. Тексты, изображения и голос попадают в Telegram независимо от локальности Codex и Whisper. Оператор бота, компрометированный Telegram-аккаунт или утечка bot token создают риск. Numeric-ID allowlist помогает против посторонних пользователей, но не компрометации вашего собственного аккаунта.

## Сообщение об уязвимости

Не публикуйте конфиги, bot tokens, Codex auth, дампы SQLite или реальные изображения/транскрипты в публичном issue. Воспроизводите на fixture данных и mock API. Диагностика должна содержать версии, классифицированные ошибки и результаты тестов без секретных значений.
